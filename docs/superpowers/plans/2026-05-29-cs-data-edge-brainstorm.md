# CS Data Edge Brainstorm And Product Completion Plan

Date: 2026-05-29

## Purpose

This document captures what the HLTV scraper still needs to become a complete product, then expands the data strategy beyond basic maps, scores, K/D, and player stats. The goal is to build the richest possible point-in-time dataset for predicting future team encounters.

The guiding product question is:

> What did we know before the match, what happened during the match, and what repeatable patterns can we turn into predictive features without leaking future information?

## Product Completion Checklist

The scraper is already close to an operator-ready MVP. To feel like a complete product, it needs these remaining pieces.

### 1. Event Tier Registry

Current behavior uses HLTV result stars plus event-name overrides. A product-grade version should have a maintained registry:

```yaml
events:
  - pattern: "IEM Cologne"
    tier: 1
    tags: ["lan", "elite", "esl"]
  - pattern: "ESL Pro League"
    tier: 1
    tags: ["league", "elite", "esl"]
  - pattern: "CCT"
    tier: 2
    tags: ["online", "regional"]
```

Why it matters:

- HLTV stars are useful but not a full business definition.
- Some event families vary by year, region, qualifier stage, and team pool.
- Modeling needs stable tier labels to compare like-for-like matches.

### 2. Fixture Validator

Add a `validate-fixtures` command that checks every parsed JSON file for:

- Schema version.
- Required fields.
- Valid teams, event, scheduled time, and status.
- Valid map names and scores.
- Winner consistency with scores.
- Best-of consistency with map count.
- Player count sanity.
- Player stat completeness.
- Tier metadata presence.

Output should be JSON plus a nonzero exit code if the dataset is not training-safe.

### 3. Completeness And Progress Dashboard

CLI JSON is good for operations, but a dashboard/report makes the scraper feel like a product.

Minimum dashboard sections:

- Total discovered, parsed, final, open, due, failed.
- Tier 1 vs tier 2 fixture coverage.
- Matches with maps, vetoes, players, and player stats.
- Backfill next page, offset, started/completed state.
- Request success/failure rates by fetcher and proxy region.
- Latest fixtures and backups.
- Worst quality warnings.

This can start as a static HTML report generated by `python -m scraper.cli report`.

### 4. Better Stats Recovery

Stats pages are the main gap. The scraper should separate match-page completion from stats-page completion:

- Match complete without player stats.
- Stats URL missing.
- Stats URL found but blocked.
- Stats URL found but parser failed.
- Map stats ID found but map stats fetch failed.
- Map stats fetched but no player rows parsed.

Add commands:

- `retry-stats-only`
- `stats-gaps`
- `show-match MATCH_ID`

### 5. Date-Based Historical Backfill

The current cursor is page-based. Product language should be date-based:

```env
HLTV_BACKFILL_STOP_DATE=2023-09-27
```

This lets the target be:

- All CS2 tier 1 and tier 2 matches.
- All matches since CS2 release.
- All matches from a specific season.

Page-based limits can remain as a safety fallback.

### 6. Alerting And Daily Digest

Alerts should cover:

- Backfill finished.
- Failure rate above threshold.
- No new matches discovered in N runs.
- Stats coverage below target.
- Daily cap reached too early.
- Disk space low.
- Backup failed.

Daily digest payload:

- New discovered.
- New final fixtures.
- New failed rows.
- Quality score.
- Tier 1/tier 2 counts.
- Backfill cursor.
- Manifest snapshot ID.

### 7. Data Contract And Snapshot Manifest

Every dataset export should include:

- Fixture schema version.
- Parser version.
- Git SHA.
- Data snapshot hash.
- File count.
- Tier coverage.
- Quality score.
- Generation timestamp.

The manifest is the bridge between scraping and modeling. A model should always be trained against a named data snapshot, not a loose folder.

### 8. Source Audit Trail

Every fixture should be traceable back to raw inputs:

- Match page URL.
- Stats page URL.
- Map stats URLs.
- Raw HTML hashes.
- Fetch timestamps.
- Parser version.
- Fetcher type.
- Proxy region.

This is useful for debugging, reproducibility, and explaining model inputs.

### 9. Admin Operations

Add safe commands so you never need to manually edit SQLite:

- `show-match MATCH_ID`
- `failed`
- `retry-failed`
- `retry-stats-only`
- `reset-backfill`
- `pause-backfill`
- `resume-backfill`
- `validate-fixtures`
- `report`
- `export-with-manifest`

### 10. Downstream Ingestion

Once a scrape run is healthy, the pipeline should optionally:

- Reparse raw HTML.
- Validate fixtures.
- Write manifest.
- Export to Betto canonical fixture directory.
- Trigger Betto ingestion.
- Write an ingestion report.

## Data Extraction Brainstorm

The strongest predictive edge will probably come from combining many weak signals:

- Structural match context.
- Team strength and form.
- Map pool and veto tendencies.
- Roster and role fit.
- Player form.
- Event pressure and schedule fatigue.
- Tactical style.
- Economy, pistol, conversion, clutch, and opening-duel patterns.
- News, interview, and broadcast information.

HLTV alone gives a good base. Demos, VODs, transcripts, and LLM extraction can make the dataset much more unique.

## Beyond HLTV: VOD, Stream Transcript, Demo, And LLM Data

HLTV gives structured results. The bigger edge may come from unstructured and semi-structured sources that markets price slowly or inconsistently.

### Stream Transcript Signals

If you transcribe broadcasts and feed them through an LLM, extract only timestamped, source-linked claims. The model should produce structured JSON with confidence and quote spans.

Useful transcript facts:

- Stand-in mentioned.
- Player illness.
- Visa/travel issues.
- Practice issues.
- Role changes.
- New IGL.
- Coach absence.
- Mental tilt.
- Team conflict rumors.
- Map preparation comments.
- Analyst desk veto expectations.
- Caster notes about unusual setups.
- Economy weakness.
- Pistol-round strength.
- Clutch reputation.
- Player confidence/body language comments.
- Recent scrim rumors, marked as low confidence.

Example output:

```json
{
  "match_id": "2390000",
  "timestamp": "00:14:32",
  "entity": "Team A",
  "signal": "stand_in",
  "value": true,
  "confidence": 0.92,
  "evidence": "Analyst says Team A are using a stand-in today.",
  "leakage_safe_before_match": true
}
```

Important rule:

- For pre-match predictions, only use transcript/VOD information published before the match starts.
- Post-match broadcast comments are useful for training tactical labels, but not as pre-match features for that same match.

### Best Positions And Positional Strength

“Best positions” can mean several measurable things:

1. **Player position strength**
   - How well a player performs from common positions.
   - Example: Mirage connector, Inferno banana, Nuke ramp.

2. **Team positional control**
   - How often a team gains/holds key map areas.
   - Example: Ancient mid control success.

3. **Opponent weakness by position**
   - Which positions or map zones opponents fail to clear.

4. **Role comfort**
   - Whether a player is playing historically strong roles/positions.

Feature examples:

- `player.position_kill_rate_90d`
- `player.position_death_rate_90d`
- `player.position_trade_rate_90d`
- `team.zone_control_success_90d`
- `team.site_hold_success_90d`
- `team.retake_success_by_site_90d`
- `opponent.entry_success_vs_position_90d`
- `roster.role_disruption_score`

### LLM Tactical Labeling

An LLM can label qualitative match traits from transcripts, analyst desks, articles, and post-match interviews:

- “slow default team”
- “aggressive CT side”
- “weak late rounds”
- “AWPer in poor form”
- “new caller”
- “map pool expanded”
- “struggling on T side”
- “tilts after economy resets”
- “wins through individual skill”
- “structured execute-heavy team”

Convert these to structured features:

- Label.
- Entity.
- Time validity window.
- Confidence.
- Source URL/file.
- Evidence quote.
- Whether safe for pre-match use.

Avoid feeding free-text directly into betting decisions. Use structured labels and confidence.

## Data Model Recommendation

Split data into layers:

1. **Raw**
   - HTML, VOD transcript, demo JSON, OCR output, source metadata.

2. **Parsed**
   - Matches, maps, vetoes, players, teams, stats, transcript claims.

3. **Validated**
   - Schema-checked, quality-scored, point-in-time safe records.

4. **Features**
   - Rolling and point-in-time feature values.

5. **Model Datasets**
   - Frozen snapshots with manifest IDs.

6. **Predictions And Evaluation**
   - Probabilities, recommendations, market prices, CLV, ROI.

## Biggest Potential Edge Sources

The likely highest edge features are:

1. **Roster disruption**
   - Stand-ins, role swaps, new IGL, short practice time.

2. **Map veto prediction**
   - Getting expected maps right before market fully prices them.

3. **Map-specific team strength**
   - Better than global team rating.

4. **Role and position matchup**
   - Especially from demos: weak anchor vs strong execute team, entry path mismatch, exploitable site.

5. **Fatigue and schedule density**
   - Many markets underweight travel, back-to-back matches, and long event days.

6. **Broadcast/news qualitative signals**
   - Illness, confidence, preparation, tactical changes, role conflict.

7. **Market movement**
   - Combining model probability with line movement and liquidity can separate real edge from stale numbers.

## Guardrails

- Never use information published after match start for pre-match predictions.
- Every feature needs an `as_of` timestamp.
- LLM-extracted claims need source, timestamp, confidence, and evidence.
- Rumor/social features should be low confidence unless confirmed.
- Raw data should always be stored before parsing.
- Every model run should cite a manifest snapshot ID.
